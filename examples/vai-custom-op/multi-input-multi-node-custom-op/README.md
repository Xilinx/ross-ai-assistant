# Multi-Input, Multi-Node — Nine Ops and Three Inputs In, One Custom Op Out

This is an example for calling the **custom op** skill (`/vai-custom-op`). You
provide a nine-node graph and a `vitisai_config.json`; everything
else — the AIE kernel, the tiling, etc is generated by the skill.

Two things make this harder than a single-node model, and both are the point of
the example:

- **Fusion.** The nine nodes have to come out as a **single** custom op, not one
  op per node. The skill has to keep the whole chain live in L1 instead of
  tiling each op on its own, and resolve the `Slice`/`Concat` pair as buffer
  layout rather than as real data movement.
- **Three real inputs.** A custom op sees at most **two** core-tile buffers
  (IFM and WTS), so `gemm_input`, `scale` and `offset` cannot each get their
  own. They have to be packed with the Tiling API and the DMA controllers —
  not by adding `Concat`/`Reshape` nodes to the ONNX graph, which would cost a
  DDR round trip. `scale` additionally fans out to both `Mul` nodes, so the
  packing has to serve both branches.

## Skills Used

- **vai-custom-op** (orchestrator) — turns the `--ops` node list into one
  cluster, prepares the hermetic workspace, spawns the worker, and gates
  integration on its compile and numeric verdicts.
- **vai-custom-op-implementation** (in the worker) — Phases 1-5: cut the
  subgraph, generate CPU reference data, write kernel + tiling + YAML, compile,
  validate under x86sim.
- **vai-aie-kernel-development** / **vai-aie-compiler-oriented-optimizations**
  and **vai-perf-analysis** — drive the Phase 5 optimization loop.

## Prerequisites

- A **Vitis AI** environment providing the VAIML compiler (`flexml`),
  `aiecompiler`, and the `VitisAIExecutionProvider`. Inside the Vitis AI Docker
  container this is already provisioned.
- For the board steps: a **VE2** board reachable over **SSH**. With no board reachable the
  skill does **not** silently skip it; it warns that correctness then rests on x86sim alone
  and that Phase 5 degrades to static metrics, and asks for explicit consent.

## Starting Point

The two files provided to you in [`input/`](input/):

| File | Role |
|------|------|
| [`model.onnx`](input/model.onnx) | The input model: a nine-node graph with three inputs and one output. |
| [`vitisai_config.json`](input/vitisai_config.json) | Compile config for `ve2`. Note it has **no `custom_ops` section**: the skill adds that. |

The graph is a `Gemm` feeding a two-branch elementwise chain that is
concatenated back together:

```
gemm_input [1296,256] -> Gemm_0 x[256,4] +bias -> gemm_output_reshape [1,1296,4]
  -> Slice_1 (channels 0:2) -> Mul_1 by scale -> Add_1 offset --.
  -> Slice_4 (channels 2:4) -> Exp -> Mul_2 by scale ----------> Concat_5
```

| Tensor | Shape | Kind |
|---|---|---|
| `gemm_input` | `float[1296,256]` | input |
| `scale` | `float[1,1296,2]` | input, consumed by `Mul_1` **and** `Mul_2` |
| `offset` | `float[1,1296,2]` | input |
| `concat_output` | `float[1,1296,4]` | output |

Only the `Gemm` weight and bias and the `Slice`/`Reshape` parameters stay
constant. The `Gemm` is skinny (N=4), so the block is bandwidth- rather than
MAC-bound and the whole chain is a single fusion target.

## How to Run

**Follow [`prompt.md`](prompt.md)**.
The single prompt in this file triggers the custom op creation flow end to end:
cut the subgraph and capture a CPU reference, generate the custom op, compile,
validate under x86sim, optimize against board timings, then stitch back into the
full model and verify end to end.

## Recorded Run

From the nine nodes the skill writes four artifacts that did not exist before:
* `custom_op_myop/myop.cpp` (the per-core kernel),
* `custom_op_myop/myop_tiling.py` (the `getTiling` function
defining the L3/L2/L1 buffers and the DMA transfers between them),
* `custom_op_myop/myop.yaml` (the op config tying the two
together), and
* `model_b.onnx` (with the nine nodes replaced by `mydomain.myop`).

It also adds a `custom_ops` entry pointing at the YAML — the only edit it makes
to the compile config.

**Validation gates.** The orchestrator will not integrate an op that has not
cleared both:

| Gate | Check |
|---|---|
| Compilation | Compilation succeeds |
| Numeric | `compare_npy.py` returns `SUCCESS` against the Phase 1b CPU reference |

## Expected Behavior

- The skill generates **all four** custom-op artifacts from the nine-node
  cluster.
- The nine nodes collapse into **one** custom op, and the three inputs are
  packed into the two available core-tile buffers by the tiling — the ONNX
  graph gains no auxiliary `Concat`/`Reshape` nodes.
- The `Exp` branch is the accuracy-sensitive one — bf16 rounding of the `Gemm`
  output is amplified exponentially, so it carries most of the error budget.
- Both gates pass, and the **integrated** model compiles and is verified end to
  end in Phase 7.
- The run ends with a `report.md` from the orchestrator. Should there have been
  multiple iterations to converge to the final custom op, the report would cover
  them all rather than only the successful one.
