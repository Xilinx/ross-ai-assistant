# 8-6859: multi-driven net on pin

**Message:** `[Synth 8-6859] multi-driven net on pin !%1! with !%2! driver pin '!%3!'`
**Severity:** CRITICAL WARNING
**Source:** Oasys Synthesis

---

## Vivado Message

```
CRITICAL WARNING: [Synth 8-6859] multi-driven net on pin out1 with 1st driver pin 'in1' [/path/to/file.v:47]
CRITICAL WARNING: [Synth 8-6859] multi-driven net on pin out1 with 2nd driver pin 'in2' [/path/to/file.v:48]
```

Vivado emits one message per driver, so a net with N drivers produces N of these
lines naming the same pin. The pin (`!%1!`) is the net being contended; each line
names one of its drivers (`!%3!`).

---

## Root Cause

Two or more sources drive the same net simultaneously. Unlike simulation, where
the resolved value may be `X`, synthesis keeps the last driver (or ORs/muxes the
drivers depending on context) and warns that the extra drivers are illegal. This
is almost always a real design bug: an unintended short between logic cones, a
signal written from two places, or a mis-wired instantiation.

---

## Common Patterns

### P1: Multiple continuous assignments to the same net

**Problematic Code:**
```verilog
wire out1;
assign out1 = in1;   // 1st driver
assign out1 = in2;   // 2nd driver -> multi-driven
```

**Recommended Fix — pick one source, or mux them explicitly:**
```verilog
wire out1;
assign out1 = sel ? in2 : in1;   // single driver, intent explicit
```

### P2: Net driven by a procedural block AND a continuous assign

**Problematic Code:**
```verilog
reg out1;
assign out1 = in1;             // continuous driver
always @(*) out1 = in2;        // procedural driver -> multi-driven
```

**Recommended Fix — drive from exactly one construct:**
```verilog
reg out1;
always @(*) out1 = sel ? in2 : in1;   // one procedural driver
```

### P3: Output port driven both internally and from the connection

**Problematic Code:**
```verilog
module child(output out1);
  assign out1 = 1'b0;          // driven inside child
endmodule

// parent also drives the same node
child u_child(.out1(net));
assign net = data;             // 2nd driver -> multi-driven on child/out1
```

**Recommended Fix — leave an output driven only by its module; drive the wire once:**
```verilog
child u_child(.out1(net));     // child drives net; remove the extra assign
```

### P4: VHDL multiple concurrent assignments to one signal

**Problematic Code:**
```vhdl
signal s : std_logic_vector(7 downto 0);
begin
  s <= a;                      -- 1st driver
  s <= b;                      -- 2nd driver -> multi-driven
```

**Recommended Fix — resolve to a single concurrent driver:**
```vhdl
s <= b when sel = '1' else a;  -- one driver, selection explicit
```

### P5: Same reg written from two `always` blocks

**Problematic Code:**
```verilog
reg q;
always @(posedge clk) q <= d1;   // 1st driver
always @(posedge clk) q <= d2;   // 2nd driver -> multi-driven
```

**Recommended Fix — merge the writers into one block:**
```verilog
reg q;
always @(posedge clk) q <= sel ? d2 : d1;   // single writer
```

## Diagnostic Steps

1. Read the pin name (`!%1!`) — that is the contended net. Collect every
   `8-6859` line for the same pin; each names one competing driver (`!%3!`).
2. Trace each driver back to its source (`assign`, `always`/`process`, or a port
   connection on an instance).
3. Decide which single source is intended, or combine them behind an explicit
   mux/priority based on a select signal.
4. Remove or gate the remaining drivers so the net has exactly one active source.

---

## Fix Strategy

1. **Keep exactly one driver per net.** Replace competing drivers with a single
   `assign`/`always`/concurrent statement, muxing on an explicit select when more
   than one value is genuinely needed.
2. **Do not drive a module output from outside** — let the owning module drive it,
   and connect the port to a wire that has no other driver.
3. **For buses**, check that overlapping slices are not each fully driving the
   same bits; drive disjoint bit ranges or select between them.
4. **True tri-state only** — if a real bus with `Z` drivers is intended, use
   proper tri-state (`assign bus = en ? val : 'z;`) with mutually exclusive
   enables; on FPGA fabric this is converted to a mux, so prefer an explicit mux.
5. Re-run synthesis and confirm all `8-6859` lines for the net are gone.
