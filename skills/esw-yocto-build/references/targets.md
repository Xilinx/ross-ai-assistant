`$BUILDDIR/conf/conf-notes.txt` is the authoritative, per-checkout list of machines and
targets. Always read it (`run_edf_build.sh --list-targets`) rather than trusting the tables
here, which record the shape of the split and can lag a release.

## The two-machine model

EDF splits a bootable system across **two builds with two different `MACHINE` values**. This
is the single most important thing to get right; a generic Yocto reflex of "one MACHINE, one
image" produces a build that silently omits half the deliverable.

| | Common machine | Board SDT machine |
|---|---|---|
| Example | `amd-cortexa78-common` | `versal-2ve-2vm-vek385-revb-sdt-seg` |
| Origin | shipped by `meta-amd-edf-bsp` | shipped by a BSP layer, or generated by `$esw-gen-machine-conf` |
| Produces | portable rootfs / disk image | `boot.bin`, OSPI/QSPI images, device trees |
| Typical targets | `edf-linux-disk-image`, `edf-platform-disk-image` | `packagegroup-boot-artifacts`, or supported individual boot recipes |
| Bootable alone | **No** | boot artifacts only, no rootfs |

Every common machine's own `@DESCRIPTION` ends with "Not bootable on its own." They set
`HW_BOOT_MODE = ""`, `SOC_ON_DISK_BOOT_BIN = ""` and `IMAGE_BOOT_FILES = ""`, so asking a
common machine for `xilinx-bootbin` yields nothing useful. Conversely the board machine
carries the hardware description and boot mode but is not where EDF expects the shared
rootfs to be built.

A complete deliverable therefore needs both runs, combined at flash/SD time.

## Common machines

Pick the one matching the board's SoC family and GPU:

| Common machine | Requires | For |
|---|---|---|
| `amd-cortexa9thf-neon-common` | `zynq-generic.conf` | Zynq-7000 |
| `amd-cortexa53-common` | `zynqmp-generic.conf` | ZynqMP without Mali-400 (CG/DR) |
| `amd-cortexa53-mali-common` | `zynqmp-generic.conf` | ZynqMP with Mali-400 (EG/EV) |
| `amd-cortexa72-common` | `versal-generic.conf` | Versal adaptive SoC |
| `amd-cortexa78-common` | `versal-net-generic.conf` | Versal NET / Gen 2 without Mali-G78AE |
| `amd-cortexa78-mali-common` | `versal-2ve-2vm-generic.conf` | Versal Gen 2 with Mali-G78AE |

Match against the `require conf/machine/<soc>-generic.conf` line in the board machine conf.
A board machine that requires `versal-2ve-2vm-generic.conf` pairs with an A78 common
machine, not an A72 one. Do not infer the GPU variant from the board name; check whether the
board machine's `MACHINE_FEATURES` mentions a Mali part.

## Rootfs and SDK targets

Built against a **common** machine:

| Target | Result |
|---|---|
| `edf-linux-disk-image` | Linux-only console image, no Xen or OpenAMP |
| `edf-platform-disk-image` | extends the Linux image with Xen and OpenAMP |
| `meta-edf-app-sdk` | application SDK |
| `container-app-hello-world` | sample container app |
| `container-devtools-edf` | container dev toolchain |

Some AMR/hybrid platforms use their own image and distro, e.g.
`DISTRO=amd-edf-small MACHINE=emb-plus-ve2302-amr bitbake emb-plus-apu-image`. Take the
`DISTRO` from `conf-notes.txt`; do not assume the default `amd-edf` applies everywhere.

## Boot-artifact targets

Built against a **board SDT** machine:

| Target | Result |
|---|---|
| `packagegroup-boot-artifacts` | Machine-dependent boot-artifact group; inspect resolved dependencies and deploy outputs |
| `xilinx-bootbin` | `boot.bin` |
| `edf-ospi` | OSPI flash image |
| `edf-qspi` | QSPI flash image |
| `kria-qspi` | QSPI image for Kria SOMs |

### Building the boot-artifact group

Accept `packagegroup-boot-artifacts` as an explicit build target. Discover its recipe and
appends through `bitbake-layers show-recipes packagegroup-boot-artifacts` and
`bitbake-layers show-appends`, then inspect the relevant files in the active layers.
Use `MACHINE=<machine> bitbake -e packagegroup-boot-artifacts` to inspect evaluated
`COMPATIBLE_MACHINE`, `DEPENDS`, `RDEPENDS` and task dependencies, including overrides.
Do not assume the group always includes `xilinx-bootbin`, `edf-ospi` or `edf-qspi`;
confirm what the current release and machine actually select.

Validate resolution without executing build tasks, then build through the existing wrapper:

```bash
${CLAUDE_SKILL_DIR}/scripts/run_edf_build.sh -m <machine> --dry-run packagegroup-boot-artifacts
${CLAUDE_SKILL_DIR}/scripts/run_edf_build.sh -m <machine> packagegroup-boot-artifacts
```

If the group is missing or incompatible, report the recipe/layer or machine mismatch and
supported alternatives. Preserve the user's requested target until they choose an alternative.
After completion, report the resolved members and nonempty firmware/image files actually
available in their deploy directories. A packagegroup is not itself a firmware image or WIC.

`conf-notes.txt` lists which board machines are valid per SoC family, split into "Linux only"
(`*-sdt-seg`, `*-sdt-full`) and "Multi-domain" (`*-multidomain`) rows.

## Where artifacts land

Query `DEPLOY_DIR_IMAGE` for each selected machine in the initialized Yocto shell. The
usual layout is `${TMPDIR}/deploy/images/${MACHINE}`, but overrides and multiconfigs may
change it. Because the two halves use different machines, the rootfs and the boot artifacts
land in **different** directories — expect two paths in the handoff, not one.
