# Maintainer notes: store layout and Vivado mechanics

These notes record how the workflow uses the XilinxCEDStore and Vivado. Model runs do not need them. The behavior below was verified on 2026.1 and re-checked on 2026.2; where the two differ, both are named.

## Store layout (per release branch, for example `2026.1`)

- `catalog/vivado_<release>.json`: catalog items (`name`, `display`, `latest_revision`, `commit_id`, `config.root`). It is regenerated by the store's own commits. Some items are stale (for example `cpm6_hdma` shares `cpm6_dma`'s folder, whose `xitem.json` lists only `cpm6_dma`), so the index keys designs by `design.xml`, not by catalog item.
- `<root>/design.xml`: Vendor, Library, Name, Version (VLNV `xilinx.com:design:<Name>:<Version>`), DisplayName, Description, entry script.
- `<root>/xitem.json`: display, description, category, `search-keywords`, `is_active`.
- `<root>/init.tcl`: `addOptions` (`dict create name ... type ... value ... value_list {"VALUE Label_words" ...}`), `updater`/`gui_updater`/`validater` blocks, `getSupportedBoards`/`getSupportedParts`, and the design-building procs.

## Retrieval without a database

`scripts/ced_store.py` resolves the branch head with `git ls-remote` and mirrors `<cache>/<sha>` with a blob-less sparse clone of the catalog and the five metadata files (about 2 MB). A new commit produces a new mirror; nothing is reused across commits. Design folders are added on demand with `git sparse-checkout add` under a per-commit file lock. Without git it falls back to the GitHub API and raw files; without network it uses Vivado's bundled copy and reports `source: bundled_offline`.

`scripts/ced_index.py` parses those files as data (JSON, XML and a Tcl word tokenizer; Tcl is never evaluated in Python) and ranks with BM25 over weighted fields. The top eight designs are fetched completely before Vivado loads the mirror, so their live support and options come from the current commit.

## Vivado behavior (verified on 2026.1, SW build 6511674; re-checked on 2026.2)

- `add_example_design_repo -repo_path <dir>` (undocumented) loads designs from any directory level above design folders and overrides bundled designs with the same VLNV (`REPO_DIRECTORY` shows the source). A single design folder is rejected as an invalid repo. `set_param ced.repoPaths` has no effect once Vivado is running.
- Designs whose supported parts are not installed are hidden (for example the CPM6 designs, which need `xc2vp3602*`).
- `instantiate_example_design -design <bd> -options {Opt.VALUE v ...} <vlnv>` builds into an existing project and block design. The `-project` form fails ("block design must be open"). **Option values are not validated**: an unknown option or value is silently ignored. The example-design object's `CONFIG.<option>` property is read-only and reads `0`.
- `ced::debug_design_info -file_name f <design>` dumps Vivado's evaluated parameter view for the current board: discrete range with labels, value, enabled, visible. The design's procs live in `::<vlnv>_example_design`; `addOptions $ed $board_part`, `update_N`, `update_gui_for_N` and `validate_N` can be called there. Updater arguments are inputs followed by outputs; the return value is a dict of outputs. `lib/ced.tcl` runs them to a fixed point to check option selections before instantiation.
- Vivado rereads a block design from disk only when the project is reopened. Closing and reopening the design keeps the in-memory copy; removing and re-adding the file crashed Vivado. Paths taken from Vivado objects must be copied to plain strings before `close_project`.
- The upstream MCP detaches commands that run longer than about two minutes (`STILL_RUNNING_DETACHED`). The CED session waits with `vivado_status` and reads the stored reply afterwards.

## IP whose customizer does not answer the metadata probe

The engine reads a parameter bank by building a scratch managed IP and running `::debug::dump_param_deps` on it, which internally builds the IP's customization object and therefore calls its `create_gui`. Some IP fail that call, and then every parameter of the cell comes back `PB_MISS` with `range_scope unavailable`. The signature in the Vivado log is always the same chain:

```
WARNING: [IP_Flow 19-466] add_param: Gui elements cannot be added inside update or validate or translate methods.
ERROR: [Ipptcl 7-17] Invalid Parameter 'Component_Name'.
ERROR: [IP_Flow 19-3476] Tcl error in create_gui procedure for IP '<probe>'
ERROR: [IP_Flow 19-3428] Failed to create Customization object
```

Surveyed on 2026.2 (build `2026.2_2026_1105_1942`, part `xcsu35p-sbvb625-2-e`), 28 IP probed:

| IP | Probe |
|---|---|
| `clk_wiz:6.0` | fails (`create_gui`) |
| `proc_sys_reset:5.0` | fails (`create_gui`) |
| `axi_protocol_converter:2.1` | fails (`create_gui`) |
| `smartconnect:1.0` | passes standalone (9 params), but a configured instance can fail through a different chain: `[Ipptcl 7-541] Unable to add MetaParam Data SC_CONFIG_ALL` → `add_meta_param` → `[IP_Flow 19-3475] init_meta_params` |
| 24 others, including `microblaze_riscv:1.0` (289 params), `system_ila:1.1` (3973), `fifo_generator:13.2` (168) | pass |

Two findings matter for the flow. First, there is no second source for the bank: `dump_param_deps` fails the same way on the BD cell's **own** already-built managed IP (`design_1_clk_wiz_1_0`, rc=1, 0 params), so the failure is not an artifact of the scratch probe, and repeated failed customizer builds in one session have segfaulted Vivado. Second, the failure is per-instance as often as per-definition, so there is no fixed deny-list to precompute.

Because of that the flow does not treat a missing bank as "unwritable". A value the cell **receives** (`PRIM_IN_FREQ`, `CLKIN1_PERIOD`, `REF_CLK_FREQ`, anything with `VALUE_SRC` `PROPAGATED`/`CONSTANT`) is still refused and the model is sent to the cell that produces it. A value the cell **drives on its own output** (`CLKOUT<n>_REQUESTED_OUT_FREQ`, `CLK_OUT<n>_PORT`) is accepted, because `propose` dry-runs the write, runs `validate_bd_design`, reads the value back and restores Phase 1 on failure — the write is checked after the fact rather than before it. On 2026.2 `set_property CONFIG.CLKOUT1_REQUESTED_OUT_FREQ 200` on a bank-less `clk_wiz_1` validates with 0 errors and propagates 200 MHz to `microblaze_riscv_0/Clk`.
