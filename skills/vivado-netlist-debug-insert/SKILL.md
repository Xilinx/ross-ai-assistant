# vivado-netlist-debug-insert

Insert ILA cores by Tcl in the open synthesized netlist, like the Vivado insertion wizard. The cores live in the open session only. The skill saves only where the user names and runs no build step of its own. Source and block design are never edited.
Use the Vivado MCP tools (`vivado_start`, `vivado_execute`, `vivado_status`, `vivado_stop`). The Tcl library is in this skill: `scripts/ila_insert.tcl`.

## Speak plain (read first)

- The user talks plain English and you write the Tcl. Describe what you plan, did and found in words: "the 32-bit register count", "everything marked for debug in u_dma", "too many signals at once, name a module".
- Show an item, a flag, a command or a code only when the user asks how or why. This holds for the skill's own commands, options, item forms and refusal codes. Vivado's own step names (save the checkpoint, `opt_design`, place, route) are the user's steps: say them in words.
- A refusal gives its reason in words and what the user can do about it. Never answer with a bare code. Take the reason from the refusals table in `references/help.md`. Never teach syntax. Names are implicit: you decide which kind of thing the user means (a register, a net, a combinational net) and call the library. The Tcl in this file and in the examples is for you only.

- When the user asks for help, "how do I", "what can you do", seems lost, or lacks what this skill needs (no synthesized design, no signal names): read `references/help.md`, or call `ila::help ?topic?` (`source <abs path>/scripts/ila_help.tcl`; it needs no design). Topics: what, where, inspect, glossary, items, process, options, refusals, clocks, limits, troubleshooting, next.
- Ask where they are with 3 or 4 short choices (only source code; a synthesized design ready; a Vivado project; not sure) before you ask for a path or signal name. Answer from the matching section in the user's words. Say only what `help.md` says, in your own words and with no syntax. Give every term (ILA, probe, capture depth, trigger) its plain meaning in half a sentence the first time. Explain each refusal from the refusals table in `help.md` as a reason in words, never as a code. With a design open, `ila::inspect` (help: `ila::help inspect`) lists what can be probed: tell the user what it found in words.

## Example
Request: "Add an ILA on the 32-bit register count in inputs/design.dcp." You run `check_input`, `plan {count}`, `apply`, then tell the user in words what was probed and relay the next steps. The Tcl is yours; the user reads "the 32-bit register count is probed on its clock". Worked example: the `vivado-netlist-debug-insert` folder under the repository's `examples/`.

## Rules

- Input is an open synthesized design. A placed or routed design is refused: Vivado would drop its placement and routing, and the user must run `opt_design`, place and route again. Say why in words and stop; never say the refusal code. Pass `-allow_state_reset 1` to `check_input` only when the user said to change the design as it is; then tell them the session may crash and unsaved work could be lost. An optimized design (not placed) gets a warning and goes on: relay it.
- No synthesized design (only RTL or XDC)? Never run synthesis. Say it is missing and tell the user to run `synth_design` or Run Synthesis.
- The skill writes no file and saves nothing by itself. It runs no `opt_design`, place, route or implementation run of its own, and never edits RTL, block design or the user's XDC. A Vivado step the user asks for runs as asked, with no comment: one they name (for example `opt_design`, place, route or the image), or the step a file they ask for is made from (a probes file is built from the built design, so it needs `opt_design`). Never suggest or offer a step they did not ask for. Run a save (`write_checkpoint -force <path>`, or `save_constraints` in a project) only when the user's request names where to save, and then run exactly that. The one file the skill may write is `ila::write_probes <file>`, only when the user asks for a probes file.
- Never `exit` and never force a save, unless the request says to (a headless run says so). Otherwise the cores exist only in the open session: tell the user to save before they close it.
- Report, do not block, for clocks and the debug hub. A warning about a clock that may stop or a hub on a suspect clock is a fact to pass on, never a reason to drop probes or to ask before going on. The user is the expert. Refusals that state a fact stay refusals (over budget, hardened connection, missing DFX hub).
- Every number and name in your report comes from a tool result in this session; if you did not measure it, write "not measured".
- Never call `vivado_stop` while a command is running. Never end your turn to ask whether to keep waiting: keep calling `vivado_status`. Only if nothing has changed for 30 minutes, report the session as hung.

## Steps

1. `vivado_start` with the working directory the user gave, then `open_checkpoint <dcp>` (or the user's open synthesized run). Load the library: `source -notrace <abs path>/scripts/ila_insert.tcl` (the notrace flag keeps Vivado from echoing the whole file into the tool result) (next to this file; it also loads `ila::help` and `ila::inspect`).
2. `ila::check_input`. It returns the architecture (`versal` or an UltraScale family). It refuses a placed or routed design (see Rules) and stops with `ILA_BLOCKED_NO_CIPS` on a Versal design with neither a CIPS nor a PS Wizard (no PS9 or PS11 processor; blocker FB-V01: report it, name the change the user must make, add nothing). `ILA: DFX ...` lines mean reconfigurable partitions: follow the DFX section and report the lines as written. `EXISTING DEBUG CORES`: tell the user, with each core's type. Plan with `-replace_existing 1` only when the line offers it and the user asked to change or replace what is probed (it deletes the old core, then creates the new one); if they asked to add probes, plan normally. Say which cores were kept or removed.
3. Turn the request into names and call `ila::plan {names} -depth N`. A name is a Vivado name pattern, matched against full hierarchical names like `get_nets -filter {NAME =~ <name>}`. You pick the names; say in words what you chose. You never tell the user a name has a kind: the library tries registers first (`<name>_reg`, then their output nets), then nets, by itself. Rules V1 to V9 (detail: `references/item-syntax.md`):
   - **A named signal or register**: its plain name (`count`). A bare name is the top level only. A path (`u_a/u_b/count`) is that exact one. `*/count` is `count` below the top at any depth ("in every instance", "all of them"; add the bare name too when `count` also exists at the top). Use it also for a large named register, so it is checked against the memory budget.
   - **A bus**: the bare bus name means every bit (`count`). One bit is its name (`count[3]`). Several bits are listed by name (`count[0] count[1] count[2]`). There is no range form: a range of bits is the list of its bit names, and a name with a colon range in it matches nothing.
   - **A family of registers or nets**: a pattern (`u_dma/data_reg*`; `*` any characters, `?` one character, brackets are literal).
   - **Marked nets**: `-filter {MARK_DEBUG}` (every net marked for debug); for one module `-filter {MARK_DEBUG && (NAME =~ u_dma/* || NAME =~ */u_dma/*)}`. The filter adds nets to the names; it never narrows them. If it finds nothing and the user says the design was built with `config_flows -mark_debug synthesis_only` (or `disable`), name that as the likely reason. Never say nothing is marked before you open the design and plan it or run `ila::inspect`.
   - **A whole module**: `u_x/*` (register outputs; skipped combinational nets are reported (N16): name them in words as an excluded class).
   - **Combinational nets**: only when the user says so. An exact name whose net is combinational is probed with a warning (W01). By pattern, `-combinational {names or globs}`, for those names only; a name listed there is not also in the name list. `-combinational {*}` is refused as too broad (N17). The words everything, all signals and all nets do NOT ask for combinational nets.
   - **An interface by its name** ("the axis interface in u_stream", "s_axi"): find its nets with one query in that module, `get_nets -hierarchical -filter {NAME =~ "u_stream/*axis*"}`, and read back the count and the bus names without bit indexes, never the whole list (it can overflow the tool output). Plan those names and say which signals you took. If nothing matches, tell the user no net in that module carries the name and ask which signals they mean. `ila::inspect` takes no module name.
   - **Match-all** ("everything", "all registers" with no module or names): plan `*` once and let the library answer. If it refuses as too broad (N17), stop: say in words that it is too many signals for one request and ask for a module, register or signal list. Do not split it into patterns or list names yourself.
   - **A name the netlist lacks**: nothing matches (N01). The reason lists where the same name exists: ask the user which one, or, when only one place fits their words, plan again with its path and say so. If it offers "Did you mean" with the same name plus a module prefix or suffix, plan again with it and say so. A name that differs by spelling: ask the user.
4. Read the plan output. Each rejection has a code and a reason. The code is yours (`references/rejection-codes.md`); tell the user the reason in words from the refusals table in `references/help.md`, and the code only if they ask. Report every rejection and never insert a rejected net. `WARNING` lines need a sentence to the user; `NOTE` lines are facts to pass on. One ILA is planned per clock net, and nets on the same physical clock share it. Each signal (a bus or a single net) gets its own probe port, so it can trigger alone or combined with OR, as in the Set Up Debug wizard. Each core has a clock verdict: `free`, `gated` or `unknown`. For `gated` or `unknown` the plan warns, names the connection it traced, and still plans the probes: relay the warning and say the skill cannot prove the clock stops. The skill never moves a debug hub's clock.
   Report each item of the request from its `REQUEST` line, which names every signal of the name: probed, the same net as another, or refused with the reason. A constant bit has no net, and a signal the optimizer removed cannot be probed. Two names for one signal are one net (`ALIAS`). For a bus give the bit indexes that exist and those that do not. A register's output net can carry another signal's name (for example a state bit whose net is named m_axis_tvalid). It is still that register's output and it is probed: say so, never report it as missing.
   If the plan returns 0 (nothing accepted, or over the memory budget), stop and report the reasons. Quote the plan's numbers for an over-budget refusal: tiles needed, tiles free, depth and width, and the largest depth that fits. Then wait: never change the depth, the signals or the memory type (block RAM or UltraRAM) on your own to make it fit. Tell the user the choices in words and do the one they pick.
5. `ila::apply`. It creates the cores in memory, sets defaults, connects clock and probes, and reads everything back. Nets Vivado silently skips are dropped and reported as N99. `ILA_NOTHING_INSERTED` means every net was refused. An `ILA_BLOCKED_*` code is a blocker; `ILA_CREATE_FAILED` carries Vivado's text: report it as it is. After `apply` the log prints `debug hub clock: <net>`: report it. On Versal 2026.2 the skill connects an undriven hub clock pin as a workaround: relay that warning in words, never its code.
6. `ila::apply` ends by printing the facts for the user's setting (`DONE`, `TO KEEP THEM`, and an AI-only note); `ila::next_steps` prints them again. Pass on the facts only: the cores are in the open design, what was saved or built (nothing, unless the user asked). Do not list, recommend or offer implementation steps. The commands, for you, when the user asks how or names a step:
   - Checkpoint session: `write_checkpoint -force <file>.dcp`, then `opt_design`, `place_design`, `route_design`, `write_bitstream`.
   - Open project: `save_constraints`, then `reset_run impl_1` and `launch_runs impl_1 -to_step write_bitstream`. Before `save_constraints`, count the project's XDC files: with one XDC file, copy it first (name the copy with a `.bak` ending) and tell the user it will be rewritten.
   - Probes file: after `opt_design`, `write_debug_probes -force <file>.ltx`; on Versal 2026.2 write it again after `route_design`, because the hub id is final only then.
   - A failed `apply` leaves some cores: do not save, run `ila::reset`.
7. Only if the user asks for a probes file: `ila::write_probes <file>`. The probes file is built from the built design, so it can be written only after `opt_design` has run in this session. A request for the probes file is a request for that step: if `opt_design` has not run, run it, then write the file, with no comment (never suggest it when the user did not ask for the file); `ila::write_probes` called before it refuses in plain words. It never overwrites without `-force 1`.
8. Report: each name asked for and every signal of it as its `REQUEST` line after apply says (never from the first and last nets alone), clock and verdict per core, rejections with reasons, every warning, the memory (block RAM) line, and what was saved, written or built (nothing, unless the user asked).

## Change a setting of a core the skill inserted

Detail and every refusal: `references/change-settings.md`. Load the library as in step 1 on the user's synthesized or `opt_design` checkpoint. A placed or routed design is refused, even after `-allow_state_reset 1`.
1. Look: `ila::change <core>` prints whether the skill made the core, its settings and the values each accepts. Only the skill's own cores change (`ILA_CHANGE_NOT_SKILL_CORE`, `ILA_CHANGE_CORE_EDITED`, `ILA_CHANGE_NO_MARKER`): tell the user the reason in words and never change the core another way.
2. Dry run: `ila::change <core> -depth 8192 -dry_run 1` (also `-memory_type`, `-strg_qual`, `-adv_trigger`, `-comparators`, `-pipe_stages`, `-probe_type`). Relay what it will set, in which order, and the memory line.
3. Ask first only when the request is ambiguous (several skill cores and no name) or the dry run adds a change the user did not ask for (capture control raises comparators to 2). Else go on. A different probe type per signal is possible, so try it before you ever say types cannot be mixed: the change sets the type of the port that carries a named signal (`-probe_types {name type ...}`), and each signal has its own port. Only part of one signal (some bits of a bus), or a core built by an earlier version of the skill, can be refused (`ILA_CHANGE_SHARED_PORT`). When a change is refused, tell the user why and offer to plan the core again with replace, but do not do it unless they ask: it deletes the core and its probes.
4. Change: the same call without `-dry_run`. Every value is read back. Relay the `CHANGED` line. The new setting is built at the next `opt_design`; say that nothing was saved or built.
5. Prove: only after the user's `opt_design`, `ila::prove_built <core>`. Report PROVEN, NOT PROVABLE or FAILED as printed. On Versal only depth and memory type are proven; the rest is read back only.

## DFX designs (partial reconfiguration)

Detail: `references/dfx.md` (Versal), `references/routes.md` (UltraScale+). Never edit source: report the required change and add nothing.

- Versal, project mode. The user opens each configuration (`open_run synth_1 -name <n> -pr_config <cfg>`): parent first, then each child with a module to probe. Give each its own `-name`: opening the next one does not close the first and the first keeps its core (measured 2026.1 and 2026.2; `current_design <n>` switches back), so do the children in the same session, no question to the user. Hubs must already be in the design (`ILA_BLOCKED_DFX_NO_HUB`). Static cores only in the parent (`ILA_BLOCKED_DFX_STATIC_IN_CHILD`). Per configuration: `check_input`, `plan`, `apply`. Facts: the cores stay in the open configuration until it is saved (`save_constraints` or `write_checkpoint`). Its implementation run needs `reset_run` first (child runs with `-to_step write_device_image`); Force up-to-date keeps old results without the new cores.
- UltraScale+ 2026.2, checkpoint session only, design with no debug yet: cores go in the static part (`NOTE D01`). Facts to pass on: `opt_design` builds the hub, and the hub's constraints need the clock constraints (`read_xdc`) read before it; read after, the crossing to the hub clock loses its constraint. Each partition needs a pblock (place stops at DRC HDPR-30): the floorplan is the user's change. Proven in software on one KU5P design, and on KCU116, VCU108 and VCU128 boards with Vivado 2026.2 daily builds. Other boards are untested: say so.
- UltraScale+ 2026.1 and earlier: Vivado refuses once the partition is flagged (`ila::plan` ends in `ILA_BLOCKED_DFX_NO_BSCAN`; `ila::apply` ends in `ILA_BLOCKED_DFX_UNSUPPORTED`). Static nets: static-first route, before the flag (`ila::static_first_check_input` instead of `check_input`, then `plan`, `apply`; `opt_design` fails on the black box (DRC INBB-3) until the RMs are linked and the flag is set). Module nets need the ILA in the module source with the 12 `S_BSCAN_*` ports: report that change, never make it.
- A greybox has nothing to insert (N18, `NOTHING TO INSERT`): a success. A design that already has debug ports or cores on UltraScale+ 2026.2 is refused: report it, never work around it.

## Advice on a routed design (separate file, read only)

Own file `scripts/ila_advise.tcl`: `source -notrace` only it. Use it when the user has a routed design with debug cores and asks about a timing problem ("is there a critical path in my ILA logic?"). Detail: `references/advise.md`.
- The user opens the routed checkpoint. Run `ila::advise`. It reads the design and changes nothing. A design that is not routed gives `ILA_ADVISE_NOT_ROUTED`: say so and stop.
- Quote the `ILA ADVISE` lines as printed. Each `HINT` carries its measured fact and source; `NO HINT` means no rule applies. Add no hint of your own, no predicted gain ("may recover 0.17 ns") and no rounded number. A core setting such as `C_CLK_INPUT_FREQ_HZ` is not the clock's frequency: the clock's period is on the path line. Say the printed limits: only the worst setup path decides, probe loading is not measured, hold has no defined fix. The user decides what to change.

## Out of scope

Only ILA cores are inserted. If the user asks for a VIO, JTAG-to-AXI Master, IBERT or System ILA, say: "This skill inserts ILA cores only. Those need to be instantiated in the design source." Do not add them; still do the ILA part. Put that sentence in your final report. The skill is not a timing or implementation tool: building, timing cost and fixes are the user's.

## Defaults

Core options for `ila::plan` (yours; the user hears them as plain words from `references/help.md`, section options): `-depth N` (1024 default; 1024 to 131072, powers of two), `-pipe_stages N`, `-strg_qual 0|1`, `-adv_trigger 0|1`, `-memory_type bram|uram` (Versal, depth 4096 or more). Change them only when the user asks. Trigger in and out (`-trigin`, `-trigout`) are refused with `ILA_OPTION_UNSUPPORTED`: measured, UltraScale+ builds no trigger ports from the setting and Versal reads it back off. Say so in words. If a depth is not accepted, ask or use the largest valid depth and say what was asked and what is in the design. `ila::apply` reads every property back: on `ILA_PROPERTY_MISMATCH` report it and do not retry. A synthesis-recoded state machine has no net named after the RTL register: plan `*FSM_onehot_<name>_reg*` and say the encoding changed. Comparators per probe: Vivado's netlist insertion cannot give different probes different comparator counts (it builds one per probe, whatever is asked); one count applies to the whole core. If the user asks for different counts per signal, say that plainly. Two cores on the same clock can do it: each core has its own count, and this skill plans one core per clock, so it does not build them. Do not offer a per-signal count and do not try one.
